## Fase 2 — Motor de recomendação em lote
Código entregue e agora rodando de ponta a ponta em produção (22/08/2026). No caminho, achamos e corrigimos duas lacunas reais:
- `game_catalog.genero` nunca era preenchido em lugar nenhum (o motor é baseado em gênero). Criado `scripts/enrich_catalog.py`, que busca gênero/tags na Steam Store API (endpoint `appdetails`) pros jogos pendentes e roda como passo antes de `generate-recommendations.py` no workflow `generate-recommendations.yml`.
- `gerar_recomendacoes()` quebrava (`nlargest` em coluna vazia) quando um usuário não tinha nenhum jogo candidato. Blindado com `continue` nesse caso.

Rodado com sucesso: 140/146 jogos do único usuário de teste ganharam gênero (6 sem classificação disponível na Steam, ficam pendentes). **0 recomendações geradas — esperado, não é bug**: com só 1 usuário sincronizado, o catálogo inteiro é a própria biblioteca dele, não sobra candidato. Precisa de mais um usuário sincronizado (ou popular o catálogo com jogos que ninguém tem) pra ver o motor recomendar algo de fato.

**Reformulação multi-gênero + preço/promoção + dial (01/09/2026):** o motor usava só o primeiro gênero de cada jogo (`genero`), descartando o resto da lista que a Steam retorna -- um MMORPG podia não receber crédito de MMO nenhum se esse gênero não fosse o primeiro. `game_catalog.tags` já guardava a lista completa (só nunca era lida). Reescrito pra usar todas as tags: afinidade por tag explodida via SQL `unnest`, score de candidato mistura máximo+média de afinidade entre as tags do jogo, desempate por popularidade log-escalada do próprio jogo, limpeza de recomendações órfãs que saem do top-N a cada rodada. Renomeado `generate-recommendations.py` -> `generate_recommendations.py` (hífen não é importável pelo pytest). Achado e corrigido um bug real de dtype (`object` em vez de `float`) via os testes novos antes de ir pra produção.

Mesma chamada à Steam Store API (`enrich_catalog.py`) agora também captura imagem, preço e desconto -- `ENRICH_MODO=preco` refaz o catálogo inteiro periodicamente (preço muda todo dia), separado do enriquecimento de gênero (que roda uma vez só por jogo, agora com limite de 5 tentativas via `tentativas_enriquecimento`). `/recommendations` retorna os campos novos + `genero_motivo` (explica a recomendação: "porque você joga muito X"); fallback de `/score/:appId` passa a comparar overlap de `tags` em vez de gênero exato. Frontend: cards agora mostram imagem, link pra loja da Steam, selo de preço/promoção e o motivo; correção de score trocou o input numérico por um dial circular arrastável (`frontend/js/dial.js`, mouse/touch/teclado); recomendações paginadas como a biblioteca (10/página).

Testes novos: `pytest` cobrindo o algoritmo (`scripts/tests/`, workflow `test-scripts.yml`), `smoke_test.sh` estendido pra `/score` e `/feedback`. Verificado com Playwright num harness local (não commitado) -- achou e corrigiu um bug real no dial: recalcular o centro do círculo a cada `pointermove` (em vez de fixar uma vez no início do arraste) dava valor errado, porque o texto do botão muda de tamanho durante o arraste e desloca o layout flex. Rodado em produção com sucesso: migration aplicada, 141 jogos com preço atualizado, 50 recomendações geradas pro usuário sincronizado.

## Fase 3 — Frontend
Código entregue e deployado em 22/08/2026: landing (`index.html`, login) e dashboard (`dashboard.html`: biblioteca, recomendações com feedback, consentimento comercial, exportar/excluir conta), HTML/CSS/JS puro, sem build. Publicado no Cloudflare Pages: `https://steam-recomendador.pages.dev`.

Como o frontend fica em domínio diferente do Worker (sem domínio próprio ainda), precisou de ajustes cross-origin no backend: cookie de sessão mudou de `SameSite=Lax` para `SameSite=None`, CORS libera `FRONTEND_URL` (variável nova no `wrangler.toml`, separada de `PUBLIC_BASE_URL` que continua sendo a URL do próprio Worker usada no OpenID), e o callback de login redireciona para `FRONTEND_URL/dashboard.html`. CORS testado via curl (preflight OK, `Access-Control-Allow-Origin` e `Allow-Credentials` corretos) — falta só o teste real no navegador (login completo + cookie cross-site aceito), que só dá pra confirmar com um usuário de verdade.

Workflow `deploy-frontend.yml` cria o projeto Pages automaticamente se não existir e publica a cada push em `frontend/**`.

**Bug real encontrado com o primeiro usuário externo (01/09/2026):** o risco anotado acima ("falta só o teste real no navegador... que só dá pra confirmar com um usuário de verdade") se confirmou — um segundo usuário conseguiu logar (linha criada em `users`) mas não conseguia abrir o dashboard, porque o cookie `SameSite=None` cross-site é tratado como cookie de terceiro e bloqueado por padrão em vários navegadores (Safari, Firefox modo estrito, Chrome). Corrigido trocando a arquitetura: em vez do frontend chamar o Worker diretamente (domínio diferente), `frontend/functions/api/[[path]].ts` (Cloudflare Pages Function) faz proxy same-origin de `/api/*` pro Worker — incluindo o fluxo OpenID da Steam (`return_to`/`realm` agora apontam pro proxy, não mais pro domínio do Worker). O cookie de sessão voltou a ser `SameSite=Lax` (agora é primeira parte). `PUBLIC_BASE_URL` removido do `wrangler.toml`/`env.ts` (não é mais necessário). Ainda falta confirmar no navegador real do segundo usuário que o login completo funciona pós-deploy.

Redesenhado em 22/08/2026 com direção visual do usuário: paleta bright-green-web (schemecolor.com), fonte Lora, botões sem cantos arredondados (sem sombra -- hover é transição suave de cor), caixa central max-width 1400px centralizada horizontalmente em telas grandes (sem cap de altura -- página rola inteira normal, sem scroll interno), modo escuro padrão com alternância via Alt esquerdo+Shift+D. Ajustes de UX depois de várias rodadas de teste visual real: hero da landing centraliza verticalmente, login da Steam abre em popup (`frontend/auth-callback.html` fecha o popup via `postMessage`, Worker redireciona o callback pra lá), biblioteca paginada (20/página, coluna de tempo centralizada, formato `horas:minutos`), assets com cache-busting automático (`?v=<hash do commit>`, injetado pelo workflow) pra nunca mais depender de hard-refresh manual, parágrafo de aviso de privacidade removido da landing a pedido do usuário.

**Lições dessa rodada (guardar pra próximas telas):**
- CSS shorthand `margin: 0 auto Npx` zera `margin-top` mesmo que outra regra mais específica tente setá-lo depois -- cuidado com especificidade ao combinar seletores de elemento (`.landing-hero p`) com seletores de classe (`.aviso-privacidade`) no mesmo elemento.
- Antes de assumir bug de cache do navegador, confirmar via `curl` direto no arquivo publicado (sem cache) que o conteúdo já está certo -- fizemos isso e realmente estava certo, mas a causa raiz nunca foi 100% confirmada (o cache-busting automático elimina a dúvida daqui pra frente, então não precisa mais investigar esse tipo de sintoma).
- Cap de altura + scroll interno na caixa (achando que resolvia "caixa vazia gigante em monitor grande") criou um problema pior (scrollbar feia, proporção esquisita) -- revertido. Only a WIDTH cap, sem cap de altura.

**Recomendações agora disparadas na hora (01/09/2026):** antes, `generate-recommendations.yml` só rodava no cron diário (05h UTC) -- um usuário novo podia esperar até 24h pra ver qualquer recomendação. Agora `POST /me/sync` (`worker/src/routes/me.ts`), depois de gravar a biblioteca, dispara esse workflow direto via GitHub API (`worker/src/lib/github.ts`, `workflow_dispatch`), sem bloquear a resposta do sync. Precisa da secret nova `GH_DISPATCH_TOKEN` no GitHub Actions (repo secrets, **não** "Agents secrets" -- mesmo erro do bloqueio de Fase 0, ver acima) com um PAT que tenha permissão de disparar workflows (`workflow` scope num token clássico, ou "Actions: Read and write" num fine-grained), repassada pro Worker como `GITHUB_DISPATCH_TOKEN` pelo `deploy-worker.yml`. Secret `GH_DISPATCH_TOKEN` cadastrada pelo usuário em 01/09/2026 -- dispatch on-demand ativo.

**Bug no primeiro deploy do proxy (01/09/2026):** o proxy same-origin acima foi criado em `frontend/functions/api/`, mas `wrangler pages deploy` procura o diretório `functions/` relativo ao working directory do comando (raiz do repo), não dentro do diretório de assets que é o argumento (`frontend`) -- confirmado rodando `wrangler pages functions build` localmente (não compilava a Function nenhuma com `functions/` dentro de `frontend/`, compilou depois de mover pra raiz). Resultado: `/api/*` nunca batia na Function, caía no fallback padrão do Pages (serve `index.html` pra qualquer rota sem match), então clicar em "Entrar com Steam" só recarregava a landing page em vez de redirecionar pra Steam. Corrigido movendo pra `functions/` (raiz do repo, irmã de `frontend/`) e adicionando `functions/**` nos `paths` do `deploy-frontend.yml`.
